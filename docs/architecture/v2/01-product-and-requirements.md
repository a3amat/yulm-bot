# 01. Продукт и требования

## Что это за продукт

SaaS-платформа «один материал — много площадок». Пользователь (автор, бренд, агентство) подключает свои аккаунты соцсетей/блогов/мессенджеров, загружает или пишет контент (статья, видео, изображение/картина), платформа адаптирует его под каждую площадку (в т.ч. с помощью ИИ) и публикует — сразу, по расписанию или пакетом. Каждый клиент живёт в изолированном workspace со своим набором подключённых аккаунтов; клиенты не видят и не пересекаются друг с другом. Продаётся по подписке (месяц/год).

## Пользовательские сценарии (user journeys)

### J1. Первый запуск (онбординг)
1. Регистрация → создание workspace «Моя студия».
2. Подключение Telegram-канала (OAuth / токен бота) и VK-сообщества.
3. Создание материала: вставка текста + загрузка картины (изображение).
4. Превью: как пост будет выглядеть в TG и VK (с учётом лимитов/форматирования).
5. Публикация в обе площадки одной кнопкой. История: запись в журнале.

### J2. Редкий автор (content-first)
Пишет статью в редакторе (Markdown/WYSIWYG), черновик версионируется. Перед публикацией нажимает «Адаптировать с ИИ»: для Telegram — сокращение до 1000 знаков + ссылка на полную статью; для блога — HTML с картинками; для Twitter/X — тред из 5 постов. Проверяет результат в diff-режиме, правит вручную, публикует по расписанию.

### J3. Агентство (несколько клиентов)
В одном аккаунте — несколько workspace'ов (или один workspace с командами/ролями): менеджер, авторы, согласующие. У каждого клиента свой набор площадок и своя история. Роли: viewer/editor/publisher/admin.

### J4. Видео/картины (медиа-тяжёлый контент)
Загрузка видео (MP4/MOV) → платформа хранит в объектном хранилище, при публикации использует прямую загрузку на площадку (YouTube Data API, VK video) либо ссылку. Изображения проходят конвейер обработки: ресайз под требования каждой сети (IG 1:1/4:5, TG фото, blog hero-image), водяные знаки (опция тарифа Pro).

### J5. Оплата и тарифы
Free trial → выбор плана (Starter/Growth/Pro, месяц/год со скидкой) → Stripe checkout → активация entitlements. Превышение лимита (например, >3 подключённых площадок на Starter) блокирует новую публикацию с понятным апселлом. История платежей и инвойсы в личном кабинете.

## Функциональные требования

| № | Требование | Приоритет |
|---|---|---|
| F1 | Мультипользовательские workspace с полной изоляцией данных | MUST |
| F2 | Подключение аккаунтов площадок через OAuth/токены, статус подключения | MUST |
| F3 | Типы контента: текст/статья, изображение, видео; смешанные посты | MUST |
| F4 | Редактор материалов: Markdown + WYSIWYG, автофронт, черновики, версии | MUST |
| F5 | Публикация: немедленно, по расписанию, пакетом на несколько каналов | MUST |
| F6 | Адаптация контента под площадку (лимиты, форматирование, media-transcode) | MUST |
| F7 | AI-переписывание/сокращение/генерация вариантов под канал | SHOULD (v1.5) |
| F8 | Журнал публикаций: кто/что/куда/когда/статус/ссылка; повторная публикация | MUST |
| F9 | Подписка month/year, лимиты тарифа, биллинг-провайдер | MUST |
| F10 | Импорт контента: RSS/webhook/загрузка файла | COULD |
| F11 | Аналитика публикаций (лайки/охваты через API площадок) | COULD (v2) |
| F12 | Публичная API + webhooks для интеграций | COULD |

## Нефункциональные требования

| Категория | Требование |
|---|---|
| Изоляция | Нулевая утечка между workspace: RLS + проверка ownership на каждом запросе; OAuth-токены только шифрованными (AES-256-GCM, ключи в KMS/Vault) |
| Надёжность | Частичный успех публикации — штатный сценарий; retry с экспонентой; идемпотентность (не публиковать дубли при повторной обработке) |
| Масштабируемость | Горизонтальное масштабление воркеров публикаций; лимитеры по площадкам (rate limits API соцсетей) |
| Производительность | UI-операции < 300 мс p95; публикация стартует < 5 с после нажатия (выполняется асинхронно) |
| Безопасность | RBAC, audit log, секреты вне кода, HTTPS everywhere, rate limit API |
| Комплаенс | GDPR-минимум: экспорт/удаление данных workspace; Terms/API-политики площадок (не обходим ограничения автопостинга) |
| Наблюдаемость | Структурированные логи, метрики (latency, queue depth, publish success rate), трейсы |

## Доменные понятия (ubiquitous language)

- **Workspace** — изолированное пространство клиента (клиент = компания/автор). Владеет аккаунтами, материалами, публикациями, подпиской.
- **Account Connection** — подключённый аккаунт площадки внутри workspace (VK-группа, TG-канал, Medium…). Хранит зашифрованные креды и статус.
- **Material (Asset)** — исходный контент: статья/видео/изображение с метаданными. Не зависит от площадок.
- **Version / Draft** — неизменяемая версия материала (редактирование создаёт новую версию; история сохраняется).
- **Channel Profile** — профиль формата канала (лимиты, поля, media-требования) — данные адаптера.
- **Publication Job** — задача «опубликовать версию V материала M в набор каналов C во время T». Порождает N **Publication Attempts** (по одному на канал) — источник истории.
- **Entitlement / Plan** — что и сколько разрешено workspace (подписка, лимиты).
- **Adaptation** — результат трансформации материала под канал (готовый payload), в т.ч. AI-варианты.

## Открытые вопросы к владельцу продукта

1. Целевой рынок/язык (РФ → ЮKassa/СБП вместо Stripe; глобально → Stripe/Paddle)?
2. Первые 3 приоритетные площадки помимо Telegram? (VK, YouTube, Instagram, X, Telegram-каналы vs чаты?)
3. Нужна ли команда/роли с первого дня или MVP «1 пользователь = 1 workspace»?
4. Кто пользователи: авторы-одиночки или агентства с клиентами (влияет на иерархию workspace)?
